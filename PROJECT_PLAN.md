# PROJECT_PLAN.md — AI Risk Manager

> **Goal:** Build a working, defense-only fraud detector for card-not-present transactions, trained and evaluated on a realistic simulated dataset, with honest precision/recall/cost metrics on a held-out test set. The end result must be understandable to a non-technical merchant, not just an ML engineer.

> **Hard constraint (non-negotiable):** This system is strictly *defense-only*. It scores/flags/explains risk. It must never generate anything that could be repurposed to commit fraud, evade detection, or reverse-engineer fraud patterns for offensive use. This constraint is baked into every module below.

---

## Architecture Overview

```
Raw data (simulator)
   → [Module 0] Ingestion & validation
   → [Module 1] EDA (read-only, produces report + charts)
   → [Module 2] Feature engineering (writes engineered dataset)
   → [Module 3] Time-based train/test split
   → [Module 4] Model training (writes model.pkl + metrics.json)
   → [Module 5] Evaluation & cost analysis (writes evaluation_report.md)
   → [Module 6] Explainability layer (wraps model at inference time)
   → [Module 7] Dashboard (reads model + engineered data, serves UI)
   → [Module 8] Documentation (README.md, written after real metrics exist)
```

Every stage is a **separate script/module** with a single clear entry point (e.g., `python -m src.ingestion`). Each stage reads from and writes to disk (parquet/CSV), so any stage can be re-run independently. No stage silently swallows errors — if input data is missing, schema doesn't match, or the model file is stale, the script fails loudly with a clear message.

All configuration (thresholds, cost assumptions, file paths, hyperparameters) lives in **one `config.yaml`**, not scattered magic numbers.

## Dataset Summary (verified against [source](https://fraud-detection-handbook.github.io/fraud-detection-handbook/Chapter_3_GettingStarted/SimulatedDataset.html))

The dataset is generated by a Python simulator from the Fraud Detection Handbook. Key facts:

| Property | Value |
|---|---|
| **Customers** | 5,000 (each with location, mean spend, spend std, transactions/day) |
| **Terminals** | 10,000 (each with location on 100×100 grid) |
| **Date range** | 183 days (2018-04-01 to 2018-09-30) |
| **Total transactions** | ~1,754,155 |
| **Fraud rate** | ~0.84% (14,681 fraudulent out of ~1.75M) |
| **Columns** | `TRANSACTION_ID`, `TX_DATETIME`, `CUSTOMER_ID`, `TERMINAL_ID`, `TX_AMOUNT`, `TX_TIME_SECONDS`, `TX_TIME_DAYS`, `TX_FRAUD`, `TX_FRAUD_SCENARIO` |

### Fraud Scenarios (3 scenarios, essential for feature engineering and explainability):

1. **Scenario 1 — High amount:** Any transaction where `TX_AMOUNT > 220` is fraud. Simple pattern; serves as a sanity check for any detector. (~978 transactions)
2. **Scenario 2 — Compromised terminal:** Each day, 2 random terminals are compromised. All transactions on those terminals in the next 28 days are fraudulent. Simulates terminal-level phishing/skimming. (~9,099 transactions)
3. **Scenario 3 — Compromised customer card:** Each day, 3 random customers are compromised. For 14 days, 1/3 of their transactions have amounts multiplied by 5× and marked fraudulent. Simulates card-not-present credential theft. (~4,604 transactions)

> **Why naive "99% accuracy" is meaningless here:** With only ~0.84% fraud, a model that predicts "legitimate" for every single transaction achieves 99.16% accuracy but catches zero fraud. This is a common interview question. We use **PR-AUC** as our primary metric, explicitly report the no-skill baseline (the fraud rate itself ≈ 0.84%), and always show precision and recall together rather than accuracy alone.

### Module 0: Data Ingestion & Validation (`src/ingestion.py`)

**Purpose:** Run the handbook's simulator to generate raw transaction data, validate the schema, and store it cleanly on disk. This module is the single entry point for data generation — no other module touches the simulator.

**Inputs:**
- Simulator parameters from `config.yaml`: `n_customers`, `n_terminals`, `nb_days`, `start_date`, `random_seed`, `radius`
- The simulator code itself (adapted from the handbook's Python functions, embedded in this module)

**Outputs:**
- `data/raw/transactions.pkl` — raw transactions DataFrame
- `data/raw/customer_profiles.pkl` — customer profiles table
- `data/raw/terminal_profiles.pkl` — terminal profiles table
- Console log with row counts, date range, fraud counts per scenario, and fraud rate

**Concrete Steps:**
1. Load parameters from `config.yaml`.
2. Generate customer profiles: `n_customers` profiles with random `(x, y)` location, `mean_amount` ~ Uniform(5, 100), `std_amount = mean_amount / 2`, `mean_nb_tx_per_day` ~ Uniform(0, 4).
3. Generate terminal profiles: `n_terminals` terminals with random `(x, y)` on 100×100 grid.
4. Associate each customer with terminals within radius `r` of their location.
5. Generate transactions per customer per day: number of transactions drawn from Poisson(`mean_nb_tx_per_day`), amounts from Normal(`mean_amount`, `std_amount`), times centered around noon.
6. Add fraud labels via the 3 scenarios described above.
7. Sort by `TX_DATETIME`, assign `TRANSACTION_ID`.
8. **Validate schema**: assert all expected columns exist, assert `TX_FRAUD` ∈ {0, 1}, assert `TX_FRAUD_SCENARIO` ∈ {0, 1, 2, 3}, assert no nulls in required columns, assert date range matches config.
9. Save to `data/raw/` as pickle files.
10. Print summary: total rows, fraud rate, fraud counts per scenario, date range.

**Libraries:** `pandas`, `numpy`, `pyyaml`, `random`, `datetime`, `os`

**Success Criteria:**
- Script runs end-to-end without errors.
- Output files exist and match expected schema.
- Fraud rate is approximately 0.8-1.0%.
- Row count is approximately 1.7M for default config.

**Risks / Edge Cases:**
- Simulator can be slow (~3 min for full dataset). This is acceptable for one-time generation, but the smoke test will use a tiny config.
- Negative amounts from the Normal distribution are handled by falling back to Uniform(0, 2×mean).
- The `pandarallel` optimization from the handbook is optional; we use standard `apply` for simplicity and portability.

**Defense-only check:** ✅ This module generates labeled data for *detecting* fraud. The simulator code itself is well-documented in a public academic handbook. The fraud scenarios describe *detection* patterns (e.g., "track terminal fraud rates") not attack techniques. No code here teaches how to evade detection.

5. **Time analysis:** transaction volume by hour-of-day; fraud rate by hour; fraud rate by day-of-week.
6. **Customer analysis:** distribution of `mean_nb_tx_per_day`, how many customers get compromised in Scenario 3, average number of available terminals per customer.

8. Generate all charts (saved to `reports/figures/`).

**Libraries:** `pandas`, `matplotlib`, `seaborn`

**Success Criteria:**
- `eda_findings.md` exists and is readable by a non-technical person.
- All charts render correctly and are saved to disk.
- Findings are consistent with known dataset properties (e.g., ~0.84% fraud rate).

**Risks / Edge Cases:**
- Large dataset may require sampling for some visualizations. Use `.sample()` when plotting scatter plots.
- Seaborn `distplot` is deprecated; use `histplot` or `kdeplot` instead.

**Defense-only check:** ✅ EDA is inherently read-only and defensive. The findings describe *what* fraud patterns look like to help detection, not how to generate them. Charts show aggregate statistics, not individual fraud instructions.

### Module 2: Feature Engineering (`src/features.py`)

**Purpose:** Build customer-level and terminal-level rolling/aggregated risk features using **only past data relative to each transaction** to avoid data leakage. Every engineered feature is documented in one sentence of plain English.

**Inputs:**
- `data/raw/transactions.pkl`

**Outputs:**
- `data/processed/features.parquet` — transactions enriched with engineered features

**Concrete Steps:**
1. Load raw transactions.
2. Sort by `TX_DATETIME` (critical for time-based features).
3. **Date/time features:**
   - `TX_DURING_WEEKEND`: 1 if Saturday/Sunday, else 0. *("Was this transaction on a weekend?")*
   - `TX_DURING_NIGHT`: 1 if hour ∈ [0, 6), else 0. *("Was this transaction at night?")*
4. **Customer-level rolling features** (windows: 1 day, 7 days, 30 days):
   - `CUSTOMER_ID_NB_TX_{window}`: number of transactions by this customer in the last {window} days. *("How many transactions has this customer made recently?")*
   - `CUSTOMER_ID_AVG_AMOUNT_{window}`: average transaction amount for this customer in the last {window} days. *("What's this customer's average spend recently?")*
   - `CUSTOMER_ID_STD_AMOUNT_{window}`: standard deviation of amounts. *("How variable is this customer's spending?")*
5. **Terminal-level rolling features** (windows: 1 day, 7 days, 30 days):
   - `TERMINAL_ID_NB_TX_{window}`: number of transactions on this terminal in the last {window} days. *("How active is this terminal?")*
   - `TERMINAL_ID_RISK_SCORE_{window}`: fraction of transactions on this terminal that were fraudulent in the last {window} days. *("What share of this terminal's recent transactions were flagged?")*

   > **Critical: Avoiding leakage.** The terminal risk score uses the **delay-based approach** from the handbook: fraud labels are only available after a delay (e.g., 7 days). So for a transaction on day `d`, the risk score only uses fraud labels from transactions up to day `d - 7`. This prevents using future information. The delay period is configurable in `config.yaml`.

6. **Amount deviation feature:**
   - `TX_AMOUNT_ZSCORE`: z-score of the transaction amount relative to the customer's rolling mean and std. *("How unusual is this amount compared to what this customer normally spends?")*
7. Drop rows where rolling features are NaN (the first `window_size` days of data). These "warm-up" rows lack historical context and would hurt the model.
8. Save enriched dataset to `data/processed/features.parquet`.
9. Print feature summary: number of features, number of remaining rows, NaN check.

**Libraries:** `pandas`, `numpy`, `pyarrow`

**Success Criteria:**
- Output parquet file exists and has expected columns.
- **No future data leakage:** for any transaction, all rolling features are computed strictly from past data (validated in smoke test).
- Feature values are reasonable (no infinities, no all-NaN columns after warm-up removal).

**Risks / Edge Cases:**
- **Data leakage** is the #1 risk. The terminal risk score MUST use delayed labels. Verify with a spot-check: pick a transaction, manually compute its terminal risk score, confirm it only uses fraud labels from before `TX_DATETIME - delay`.
- Rolling window computations on ~1.7M rows can be slow with naive loops. Use `pandas.groupby().rolling()` or a vectorized approach.
- Some customers may have very few transactions, leading to high-variance rolling stats. This is acceptable — the model should learn to handle it.

**Defense-only check:** ✅ All features describe *defensive signals* — "is this amount unusual for this customer?" or "has this terminal seen fraud recently?" No feature encodes information about how to avoid detection. The terminal risk score specifically uses delayed labels, making it impossible to reconstruct real-time fraud patterns.

### Module 3: Train/Test Split (`src/split.py`)

**Purpose:** Split the dataset by time (not randomly!) to simulate real deployment. The model trains on earlier days and is evaluated on later days it has never seen.

**Inputs:**
- `data/processed/features.parquet`
- `config.yaml` (specifies split point, e.g., `train_end_day`, `test_start_day`)

**Outputs:**
- `data/processed/train.parquet`
- `data/processed/test.parquet`
- Console log with row counts, fraud rates, and date ranges for each split

**Concrete Steps:**
1. Load `features.parquet`.
2. Read `train_end_day` and `test_start_day` from config. Default: train on days 0–120, test on days 128–182 (7-day gap to prevent label leakage from the delay-based terminal features).
3. Filter: `train = features[features.TX_TIME_DAYS <= train_end_day]`.
4. Filter: `test = features[features.TX_TIME_DAYS >= test_start_day]`.
5. Validate: assert train and test have zero temporal overlap. Assert both have non-zero fraud rates.
6. Print summary: train rows, test rows, train fraud rate, test fraud rate, date ranges.
7. Save to `data/processed/train.parquet` and `data/processed/test.parquet`.

**Libraries:** `pandas`, `pyarrow`, `pyyaml`

**Success Criteria:**
- Train and test sets have zero temporal overlap.
- Both sets have non-trivial fraud counts (> 100).
- There is a gap between train end and test start (≥ delay period used in feature engineering).

**Risks / Edge Cases:**
- **The gap is critical.** Without it, the terminal risk features in the test set would partly use training-period fraud labels that the model saw during training. This would inflate test-set performance. The gap must be ≥ the delay used in Module 2.
- If the split point is too late, the test set will be too small. If too early, training data is limited. The default (120/128) gives ~70% train, ~30% test.

**Defense-only check:** ✅ Splitting data is a standard ML practice. No offensive information is created or exposed.

### Module 4: Model Training (`src/train.py`)

**Purpose:** Train two models — a **logistic regression baseline** and a **LightGBM gradient-boosted tree** — on the training set. Handle class imbalance properly. Save models and training metrics to disk.

**Inputs:**
- `data/processed/train.parquet`
- `config.yaml` (feature columns, label column, LightGBM hyperparameters, class weight strategy)

**Outputs:**
- `models/baseline_lr.pkl` — trained logistic regression
- `models/model.pkl` — trained LightGBM model (this is the primary model)
- `models/feature_columns.json` — list of feature columns used (ensures consistency at inference time)
- `models/metrics_train.json` — training-time metrics (train AUC, etc.)

**Concrete Steps:**
1. Load `train.parquet`.
2. Read feature columns from config. Exclude: `TRANSACTION_ID`, `TX_DATETIME`, `CUSTOMER_ID`, `TERMINAL_ID`, `TX_FRAUD`, `TX_FRAUD_SCENARIO`, `TX_TIME_SECONDS`, `TX_TIME_DAYS`.
3. Separate `X_train` (features) and `y_train` (`TX_FRAUD`).
4. **Baseline: Logistic Regression.**
   - Use `sklearn.linear_model.LogisticRegression` with `class_weight='balanced'`.
   - Fit on `X_train`, `y_train`.
   - Log train ROC-AUC and PR-AUC.
   - Save to `models/baseline_lr.pkl`.
5. **Primary: LightGBM.**
   - Use `lightgbm.LGBMClassifier`.
   - Handle class imbalance via `scale_pos_weight = (count_negatives / count_positives)`. This is preferred over SMOTE because SMOTE can create synthetic points that leak future patterns in a time-series context.
   - Hyperparameters from `config.yaml` (defaults: `n_estimators=300`, `max_depth=6`, `learning_rate=0.05`, `num_leaves=31`, `min_child_samples=50`, `subsample=0.8`, `colsample_bytree=0.8`).
   - Fit on `X_train`, `y_train`.
   - Log train ROC-AUC and PR-AUC.
   - Save to `models/model.pkl`.
6. Save feature column list to `models/feature_columns.json`.
7. Save training metrics to `models/metrics_train.json`.
8. Print summary: both models' train metrics side-by-side.

**Libraries:** `lightgbm`, `scikit-learn`, `pandas`, `numpy`, `joblib` (for model serialization), `json`

**Why LightGBM?**
- Industry-standard for tabular fraud detection (fast, handles imbalance well, interpretable via feature importance/SHAP).
- This is what most real fraud teams use, making it easy to explain in an interview.

**Why NOT SMOTE?**
- SMOTE generates synthetic minority samples by interpolating between existing ones. In a time-series context, this can create "future" data points that leak information. Using `scale_pos_weight` (cost-sensitive learning) avoids this entirely.

**Success Criteria:**
- Both models train without errors.
- Model files are saved and loadable.
- LightGBM train PR-AUC meaningfully exceeds the no-skill baseline (fraud rate ≈ 0.84%).
- LightGBM train PR-AUC > logistic regression train PR-AUC (gradient boosting should outperform the linear baseline on this dataset).

**Risks / Edge Cases:**
- LightGBM may overfit with too many estimators or too deep trees. Monitor train vs. validation performance. Include early stopping if needed.
- `scale_pos_weight` assumes binary classification. Verify `y_train` only contains 0 and 1.
- Feature columns must be exactly the same at train and inference time. The `feature_columns.json` file ensures this.

**Defense-only check:** ✅ The model learns to *detect* fraud, not to *commit* it. Feature importances show which signals the model uses for detection (e.g., "terminal risk score is high" → flag), which helps the merchant understand and trust the system. The model's internals are standard gradient-boosted trees with no adversarial components.

### Module 5: Evaluation & Cost Analysis (`src/evaluate.py`)

**Purpose:** Compute comprehensive metrics on the **held-out test set**, build a cost model (FP cost vs. FN cost), pick and justify a recommended threshold, and produce an evaluation report in plain language.

**Inputs:**
- `data/processed/test.parquet`
- `models/model.pkl` (primary LightGBM model)
- `models/baseline_lr.pkl` (for comparison)
- `models/feature_columns.json`
- `config.yaml` (cost assumptions: `cost_false_positive`, `cost_false_negative`, `average_transaction_amount`)

**Outputs:**
- `reports/evaluation_report.md` — plain-language evaluation with embedded charts
- `reports/figures/pr_curve.png` — Precision-Recall curve
- `reports/figures/roc_curve.png` — ROC curve
- `reports/figures/confusion_matrix.png` — at chosen threshold
- `reports/figures/cost_vs_threshold.png` — expected cost at each threshold
- `models/metrics_test.json` — test metrics (PR-AUC, ROC-AUC, precision, recall, F1, confusion matrix, recommended threshold)

**Concrete Steps:**
1. Load test data and both models.
2. Generate predicted probabilities for both models.
3. **Threshold-free metrics:**
   - PR-AUC (primary metric) for both models.
   - ROC-AUC for both models.
   - Plot PR curve and ROC curve (both models on same plot for comparison).
   - Report no-skill baseline for PR-AUC (= fraud rate in test set).
4. **Cost model:**
   - Define costs from config:
     - `cost_FP`: cost of a false positive (manual review cost + customer friction). Default: $5.
     - `cost_FN`: cost of a false negative (chargeback + goods loss). Default: average transaction amount of fraudulent transactions in the test set (computed dynamically, typically ~$100-250).
   - For each threshold in [0.01, 0.02, ..., 0.99]:
     - Compute confusion matrix (TP, FP, TN, FN).
     - Expected cost = `FP × cost_FP + FN × cost_FN`.
   - Plot expected cost vs. threshold.
   - Find the optimal threshold (minimizes expected cost).
5. **Threshold-based metrics** at the optimal threshold:
   - Precision, Recall, F1.
   - Confusion matrix (plot as heatmap).
6. **Comparison scenarios** (for the report):
   - "Flag nothing": total cost = all fraud transactions × `cost_FN`.
   - "Flag everything": total cost = all legitimate transactions × `cost_FP`.
   - "Our model at optimal threshold": total cost from step 4.
   - Report expected $ savings as a single clear number.
7. Write `reports/evaluation_report.md` in plain language.
8. Save `models/metrics_test.json`.

**Cost Assumptions Rationale (documented in config and report):**
- **False Positive ($5):** A legitimate transaction flagged as fraud costs the merchant a manual review (~3-5 minutes of analyst time) plus the risk of annoying the customer. This is a conservative estimate.
- **False Negative ($100-250 dynamic):** A fraudulent transaction that goes undetected results in a chargeback (the merchant loses the transaction amount plus a chargeback fee). We use the actual average fraud transaction amount from the test set for realism.

**Libraries:** `scikit-learn` (metrics, confusion_matrix), `matplotlib`, `pandas`, `numpy`, `json`

**Success Criteria:**
- LightGBM PR-AUC is significantly above the no-skill baseline and above the logistic regression baseline.
- The cost analysis shows clear $ savings vs. "flag nothing."
- The evaluation report is readable by a non-technical person and includes the rationale for the chosen threshold.
- All numbers reported are honest — if PR-AUC is 0.55, we report 0.55 with an explanation, not an inflated number.

**Benchmark Targets (goals, not mandates):**
- **PR-AUC:** Clearly above the no-skill baseline (~0.008), aiming for 0.40-0.70 range with good feature engineering.
- **Recall at chosen threshold:** aim for ≥ 60% at a business-acceptable precision (guided by the cost analysis, not cherry-picked).
- **Cost reduction:** "our model" cost should be meaningfully less than "flag nothing" cost.

**Risks / Edge Cases:**
- The optimal cost threshold depends heavily on the `cost_FP` / `cost_FN` ratio. A sensitivity analysis showing how the optimal threshold changes for different ratios would be valuable (stretch goal).
- If the test set has very few fraudulent transactions, metrics will have high variance. Verify test set has sufficient fraud count.

**Defense-only check:** ✅ Evaluation metrics measure how well the system *detects* fraud. The cost model helps merchants understand the financial impact of detection. No information is provided about how to evade the model or which specific patterns it misses in a way that could be exploited offensively.

### Module 6: Explainability Layer (`src/explain.py`)

**Purpose:** For any flagged transaction, produce a short, non-technical explanation of *why* it was flagged (e.g., "This amount is much higher than this customer normally spends" rather than raw SHAP values). This module wraps the model at inference time.

**Inputs:**
- `models/model.pkl`
- `models/feature_columns.json`
- A single transaction (or batch) as a DataFrame row

**Outputs:**
- A risk score (probability)
- A list of top contributing features with plain-English explanations
- Optional: SHAP waterfall plot for technical users

**Concrete Steps:**
1. Load the model and feature columns.
2. **SHAP integration:**
   - Create a `shap.TreeExplainer` for the LightGBM model (one-time, cached).
   - For each transaction, compute SHAP values.
3. **Feature-to-English mapping:**
   - Define a mapping dictionary that translates each feature name into a plain-English template:
     - `TX_AMOUNT` → "The transaction amount (${amount})"
     - `TX_DURING_WEEKEND` → "This transaction was on a weekend"
     - `TX_DURING_NIGHT` → "This transaction was at night"
     - `CUSTOMER_ID_AVG_AMOUNT_1` → "This customer's average spend in the last day"
     - `CUSTOMER_ID_NB_TX_1` → "This customer's number of transactions in the last day"
     - `TERMINAL_ID_RISK_SCORE_7` → "This terminal's fraud rate in the past week"
     - `TX_AMOUNT_ZSCORE` → "How unusual this amount is compared to this customer's typical spend"
     - (and so on for all features)
4. **Generate explanation:**
   - Sort SHAP values by absolute magnitude.
   - Take top 3 contributing features.
   - For each, generate a sentence: "{plain_english_name} pushed the risk score {up/down}."
   - If the top feature is `TX_AMOUNT_ZSCORE` and value is high: "This amount is much higher than what this customer normally spends."
   - If the top feature is `TERMINAL_ID_RISK_SCORE_7` and value is high: "This terminal has seen an unusual number of fraudulent transactions recently."
5. **API:** Expose two functions:
   - `score_transaction(transaction_row) → (probability, risk_level)` where risk_level ∈ {"low", "medium", "high"} based on thresholds from config.
   - `explain_transaction(transaction_row) → {"score": float, "risk_level": str, "top_reasons": [str, str, str], "shap_values": dict}`.
6. Ensure explanations are strictly defensive: they explain *why the system flagged something*, never *how to avoid being flagged*.

**Libraries:** `shap`, `lightgbm`, `pandas`, `numpy`, `joblib`

**Success Criteria:**
- `explain_transaction()` produces a score and 3 plain-English reasons for any input transaction.
- Explanations are grammatically correct and understandable to a non-technical merchant.
- SHAP values sum correctly (SHAP base value + sum of SHAP values ≈ model output).

**Risks / Edge Cases:**
- SHAP computation for a single transaction is fast (~10ms for TreeExplainer), but for large batches, consider batch processing.
- Some features may have near-zero SHAP values. If all top-3 are negligible, say "No single factor strongly contributed to this score — the transaction appears routine."
- The plain-English mapping must be maintained as features are added/removed.

**Defense-only check:** ✅ Explanations are phrased from the *defender's perspective*: "This amount is unusual for this customer" (helps the merchant investigate), NOT "To avoid detection, keep amounts below X" (would help a fraudster). The explanation templates are explicitly designed to be non-invertible — knowing why a transaction was flagged does not teach someone how to avoid being flagged, because the features interact nonlinearly in the model.

### Module 7: Dashboard / Demo (`src/dashboard.py`)

**Purpose:** A minimal, clean Streamlit dashboard that shows model health, a transaction list with risk scores, and click-to-expand explanations. Designed for a non-technical merchant audience, with technical detail available on demand.

**Inputs:**
- `models/model.pkl`
- `models/feature_columns.json`
- `models/metrics_test.json`
- `data/processed/test.parquet` (as demo data)
- `config.yaml`

**Outputs:**
